1. What is Aeroflutter? What Did We Build?

Aeroflutter is a smart attendance tracking system built for a company that wants to make sure employees are physically present at the office before they can mark their attendance. It has two parts:

PartWho uses itWhat it does
📱 Mobile AppEmployeesSign up, register face, check in/out daily using GPS + face scan
🖥️ Web DashboardOwner / HRSee all attendance records, employee list, reports

This document covers the mobile app journey from zero to a working APK file.

🎯 What makes this app special? A normal attendance app just asks you to click "Check In." Aeroflutter verifies three things before accepting:
  1. Your identity — Face scan matches your registered face
  2. Your location — You must be within 50 metres of the office
  3. Your account — You must be logged in with your company email

3. The Database — Where All Data Lives

The database is like a filing cabinet. Instead of paper files, it stores digital information — employee names, GPS coordinates, face data, and attendance records — all securely in the cloud.

We used Supabase as our database. It's hosted online, so data is safe even if your computer crashes. We created four tables (think of each as a separate drawer in the filing cabinet):

Table NameWhat it stores
employeesName, email, phone, office GPS coordinates captured at signup, face encoding data, whether onboarding is complete
attendanceEach check-in and check-out event — employee ID, time, GPS location at check-in/out, status
audit_logsA detailed history of every action — including failed attempts, with reasons
officesOffice locations (for future multi-office support)
🔒 Security Rules (RLS — Row Level Security) We set up rules so that employees can only see their OWN data. An employee cannot see another employee's attendance records. Only the owner/admin can see everything. This is like each employee having their own locked drawer.

✅ How login security works When you type your password, Supabase checks it against its secure database. It never stores the actual password — it stores an encrypted version (called a hash). Even if someone hacked the database, they couldn't read passwords.

We also built an AuthContext — think of this as a central "memory" for the app. Once you log in, the app remembers your session so you don't have to log in again every time you open it.

5. Phase 2 — GPS Capture at Signup

Imagine every new employee, on their first day, stands inside the office and the app takes a "GPS photo" of exactly where they are. This becomes their office anchor point forever. When they check in later, the app compares their current location to this saved point.

We added a critical feature to the Signup Screen: before submitting the form, the app captures the employee's GPS location. This GPS point becomes their permanent "office location" — stored as latitude and longitude in the database.

⚠️ Important Rule We Enforced Employees must sign up from inside the office. Their sign-up GPS coordinates become the reference point for all future check-ins. If they sign up from home, check-in will never work for them.

How GPS verification works at check-in:

We used the Haversine Formula — a mathematical calculation that computes the real-world distance (in metres) between two GPS coordinates, accounting for the Earth's curvature.

The threshold is 50 metres. If you're within 50m of your signup location, you're considered "at the office." If not, the Check-In button is disabled.

6. Phase 3 — Face Registration (Onboarding)

Think of this like a fingerprint scanner at a door. The first time, you press your finger and the scanner "learns" your fingerprint. Every time after, it compares your finger to what it learned. We did the same thing with faces — using the front camera instead of a fingerprint reader.

After an employee logs in for the first time, they are taken to the Face Registration screen before they can use the app. This happens only once.

🤳 How Face Registration Works — Step by Step
1
The app opens the front camera
2
Google's on-device AI (expo-face-detector / ML Kit) scans the camera 2 times per second, looking for a face
3
When a face is found, it identifies 8 key landmarks: left eye, right eye, nose tip, left mouth corner, right mouth corner, left cheek, right cheek, bottom of mouth
4
These 8 landmark positions are normalized — converted to ratios relative to the face size, so they work regardless of how close or far you are from the camera
5
The 8 normalized coordinate pairs are saved to the Supabase database as the employee's "face encoding"
6
The employee's record is marked as is_onboarded = true — they won't see this screen again
🧠 How Face Comparison Works at Check-In At check-in, the app captures a fresh face scan and compares the 8 landmark positions to the stored ones. It calculates the "distance" between the two sets of points — if the difference is less than 0.25 (our threshold), it's a match. The comparison happens entirely on the device — no photo is sent anywhere.

8. All the Errors We Faced & How We Fixed Them

Building an app never goes smoothly in one shot. Here is every significant error we encountered, explained simply, and how we solved it.

❌ Error 1: PowerShell blocked npx from running

What happened: When we tried to start the development server by typing npx expo start in the terminal, Windows showed: "File cannot be loaded because running scripts is disabled on this system."

Why it happened: Windows PowerShell has a security setting that blocks .ps1 script files (a type of program file) from running. The npx command uses such a file.

Windows is like a security guard who won't let certain staff into the building. We found a back door — a different version of the same command that the guard allows.
✅ Fix: We changed npx to npx.cmd — the .cmd version is a batch file (not a .ps1 script), which Windows allows freely.
❌ Error 2: ERR_PACKAGE_PATH_NOT_EXPORTED (Metro internal paths blocked)

What happened: When we ran the server on Node.js version 24, we got an error about "package path not exported" for Metro (the tool that bundles the app code).

Why it happened: Node.js version 24 became strict about package access rules. Metro (version 0.84.4) has internal folders it uses, but didn't officially "announce" those folders in its configuration file. Node 24 enforced this rule strictly and blocked access.

Imagine an office building where employees need keycards to access different floors. Metro had an internal staircase it used, but never listed it in the official building directory. New strict security (Node 24) found it wasn't listed and locked the door.
✅ Fix: We edited Metro's configuration file to officially add those internal paths to its "allowed access" list. We patched the file node_modules/metro/package.json to include "./src/*": "./src/*.js".
❌ Error 3: MetroHmrServer is not a constructor (Node 24)

What happened: After fixing Error 2, a new error appeared: "MetroHmrServer is not a constructor." This happened when using Node.js version 24.

Why it happened: Metro's "Hot Module Replacement" server (which lets the app update instantly when you change code) was written using a newer JavaScript export style. But the code that imports it expected the old style. Node 24 changed how this export/import works, causing a mismatch.

It's like ordering a product and receiving the box inside-out — everything is there, but you can't open it the normal way.
✅ Fix: We switched from Node.js 24 to Node.js 18 (using a tool called nvm-windows). Expo SDK 49 was designed for Node 16–18.
❌ Error 4: configs.toReversed is not a function (Node 18)

What happened: After switching to Node 18, a different error appeared: "configs.toReversed is not a function."

Why it happened: The Metro config loader used a JavaScript array feature called toReversed(), which was only added in Node.js version 20. Node 18 doesn't have it.

It's like asking someone who learned English in 2015 to use slang that was invented in 2022 — they simply don't know that word exists yet.
✅ Fix: We directly edited the Metro config loader file (metro-config/src/loadConfig.js) and replaced configs.toReversed() with the equivalent older code: [...configs].reverse() — which does the same thing but works in Node 18.
❌ Error 5: npm install wiped our patches

What happened: At one point, the user ran a command that reinstalled all packages. This deleted all our manual fixes to the Metro files.

Why it happened: npm install downloads fresh copies of all packages from the internet, completely replacing any changes we had made manually.

Imagine you repaired a borrowed book by taping some pages. Then the library recalled it and gave you a fresh unrepaired copy.
✅ Fix: We re-applied all the patches (metro/package.json exports fix + loadConfig.js toReversed fix) from scratch. We also noted this as a fragile point.
❌ Error 6: MetroHmrServer is not a constructor (Node 18, different cause)

What happened: Even on Node 18, after all the fixes above, a new version of the "MetroHmrServer" error appeared.

Why it happened: Metro's HmrServer module (which handles live code updates) exports its main class using the modern JavaScript "default export" style. But the Expo CLI code that imports it was written expecting the older "direct export" style — it got the wrapper box instead of the class inside it.

The module handed over a gift-wrapped box, but the receiver expected the gift directly. They didn't know to unwrap it.
✅ Fix: We patched Expo CLI's resolveFromProject.js file for both importMetroHmrServerFromProject and importMetroCreateWebsocketServerFromProject to add the ".default" unwrapping step: mod.__esModule && mod.default ? mod.default : mod
❌ Error 7: "Tailwind CSS not configured with NativeWind preset"

What happened: When we set up NativeWind (a styling library), we got an error about the preset not being configured.

Why it happened: NativeWind version 4 requires a special "preset" line in the Tailwind config file. We had missed adding it.

✅ Fix: Added presets: [require('nativewind/preset')] to tailwind.config.js.
❌ Error 8: "Something went wrong" on Expo Go (NativeWind v4 incompatibility)

What happened: When scanning the QR code on the phone, Expo Go showed "Something went wrong" and crashed.

Why it happened: NativeWind version 4 (a CSS styling system for React Native) requires React Native 0.73 or newer. Our app uses React Native 0.72 (Expo SDK 49). NativeWind v4's internal modules were not compatible.

It's like installing a 2024 car part into a 2022 car — the part is too new and doesn't physically fit the mounting points.
✅ Fix: We completely removed NativeWind from the build pipeline — changed babel.config.js back to plain Expo preset, removed withNativeWind from metro.config.js, and removed the CSS import from App.js. Since all our screens use React Native's built-in styling (not NativeWind's CSS classes), nothing visual changed.
❌ Error 9: Wrong import paths in screen files

What happened: Several screens (Login, Forgot Password, Email Verification) were importing from the wrong folder path.

Why it happened: The screens are inside src/screens/auth/ — two levels deep. The imports were written as if they were only one level deep.

Like giving someone directions to your house starting from the wrong street — they're close but they'll end up at the wrong door.
✅ Fix: Changed all imports from '../context/AuthContext' to '../../context/AuthContext' — one extra ../ to go up one more folder level.
❌ Error 10: signup_latitude / signup_longitude NOT NULL constraint

What happened: The original signup code would crash with a database error because it wasn't providing the GPS coordinates when creating a new employee record.

Why it happened: The database was designed to require GPS coordinates for every employee (NOT NULL constraint). But the original signup function didn't collect GPS at all.

✅ Fix: We redesigned the Signup Screen to capture GPS location before the form is submitted, and pass those coordinates into the employee creation function.
